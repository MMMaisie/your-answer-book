# Existing Render service deployment

This package updates the existing service; it does not create a service or change an account's billing plan.

## Current verification status

- Chinese and English UI, all 64 cards, chart terms, teaching example and policy are implemented.
- Existing readings can be translated on explicit request. Paid access applies to the same reading in both languages; no second checkout is required.
- 43 local tests pass, including all 4,096 coin combinations, time-zone boundaries, owner privacy, mocked Stripe fulfillment and translation caching.
- Real DeepSeek requests, Stripe checkout completion and Render deployment have NOT been run in the editing environment. No working secrets or provider tools were available to this run.
- Responsive CSS supports narrow screens. No actual mobile-browser visual acceptance test has been completed.

## Update the existing repository and service

1. Back up the existing reading database and retain the existing service, Stripe product/price and environment variables.
2. Put the package contents (app.py, hexagrams.py, english_hexagrams.py, i18n.py, templates/, static/, requirements.txt) in the repository directory used by Render. Do not commit credentials or databases.
3. In the existing service, match the root directory to those files. Build: `pip install -r requirements.txt`. Start: `gunicorn app:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120`. Health check: `/healthz`.
4. Reuse DEEPSEEK_API_KEY, STRIPE_SECRET_KEY, STRIPE_PRICE_ID and STRIPE_WEBHOOK_SECRET. Also verify persistent FLASK_SECRET_KEY, PUBLIC_BASE_URL (or Render's RENDER_EXTERNAL_URL), SUPPORT_EMAIL, DB_PATH and STORAGE_DURABLE. COOKIE_SECURE=1, TRUST_PROXY=1, APP_ENV=production. Never replace unrelated environment variables.
5. If using SQLite for paid readings, confirm the existing persistent disk and DB_PATH refer to the same durable database. Move/backup existing data deliberately before changing paths. A disk is not provisioned by this package. Do not merely set STORAGE_DURABLE=1 on ephemeral storage.
6. Deploy the new repository commit. Confirm `/healthz` reports `v5-bilingual-1` and `languages: ["zh", "en"]`, and inspect startup/migration logs. Retain a rollback commit and database backup.

Render references: https://render.com/docs/web-services ; https://render.com/docs/configure-environment-variables ; https://render.com/docs/disks

## Stripe end-to-end acceptance

The bound checkout is created by POST `/r/<private-access>/checkout`. Do not use a generic standalone payment link: it cannot by itself identify and unlock the correct reading.

Webhook: `https://your-answer-book.onrender.com/stripe/webhook`. Listen for `checkout.session.completed` and `checkout.session.async_payment_succeeded`; the secret must belong to the same endpoint and mode as the API key and price. The redirect landing URL is generated by the backend, `/payment/success/<seed>?session_id={CHECKOUT_SESSION_ID}`.

Use a Stripe testing environment/sandbox with matching test keys and test price. Complete hosted Checkout with Stripe's documented test details there. Verify the session's payment_status is paid, webhook delivery succeeds, the matching reading unlocks, and refreshes create neither extra payments nor model calls. Also test cancellation, signature failure, unpaid return and another reading's session. Existing tests cover these server-side cases with mocks; mocks do not establish real provider delivery.

Do not use a live key with a test card or manufacture a live charge for testing. Real customer payment is a separate step performed by the customer. Read-only price retrieval does not prove payment completion.

Stripe references: https://docs.stripe.com/testing ; https://docs.stripe.com/checkout/fulfillment

## AI and mobile acceptance

Run `python scripts/check_services.py` in a configured environment for a credential-free summary and read-only Stripe price check. `python scripts/check_services.py --ai` makes two real DeepSeek requests using synthetic questions and prints their exact chart inputs beside the generated output. Compare named hexagrams, moving positions, kin, self/counterpart and calendar. Check the English headings and translated terms. Reject invented people, dates or certainty. This checks consistency and delivery, not ability to predict future events.

Use 360, 390 and 430 px phone widths plus a desktop width. Check form inputs, six throws, reset/mode switching, language switching, card dialog (close/Escape), still and moving charts, detail-column scrolling, readable English titles, private reading translation and hosted checkout return. Confirm no whole-page horizontal overflow; only the expanded technical table may scroll horizontally.
